# 재고 소진 경보 에이전트

매일 아침 제품별 "남은 판매 가능 일수"를 계산하고, 그 값이 필요 일수(리드타임 + 안전 재고 일수)보다 짧은 제품을 슬랙으로 알리는 Python 프로그램입니다.

같이 제출하는 문서: `docs/운영설계메모.md`, `docs/AI도구사용메모.md`.

## 실행 방법

**환경 세팅** (Python 3.10 이상)

```bash
python -m venv .venv               # 맥·리눅스는 python3 -m venv .venv
source .venv/bin/activate          # 맥, 리눅스
source .venv/Scripts/activate      # Windows Git Bash
pip install -r requirements.txt
cp .env.example .env               # 슬랙 웹훅·API 키를 쓸 때만. 없어도 돌아갑니다
```

**실행**

```bash
python -m stockout_alert --run-date 2026-10-06          # 드라이런: 슬랙에 보내지 않고 터미널과 output/에 결과를 남김
python -m stockout_alert --run-date 2026-10-06 --send   # 슬랙으로 실제 발송 (.env의 SLACK_WEBHOOK_URL 필요)
```

| 옵션 | 뜻 |
|---|---|
| `--run-date YYYY-MM-DD` | 기준일. 생략하면 오늘(한국 시간). 과제 데이터는 `2026-10-06` |
| `--send` | 슬랙으로 실제 발송. 생략하면 드라이런 |

**테스트**

```bash
python -m pytest -q
```

## 발견한 데이터 문제와 처리 방법

**1. 채널 표기가 통일돼 있지 않음 (38행)**
- 발견: `sales_daily.csv`에 `amazon_us`와 `Amazon US`가 섞여 있습니다. 둘이 같은 날 같이 나온 적은 없습니다.
- 처리: 소문자로 바꾸고 공백을 밑줄로 통일합니다. 그래도 모르는 채널이면 행은 남기고 "모르는 채널"로 표시합니다.
- 그대로 두면: 같은 제품의 판매가 두 채널로 쪼개져 하루 판매 속도가 실제의 절반쯤으로 보입니다.

**2. 완전히 똑같은 행이 반복됨 (21행)**
- 발견: SKU-03의 9/28~10/4 7일치가 세 채널 모두 두 번씩 찍혀 있습니다(날짜·제품·채널·수량 전부 같음).
- 처리: 네 값이 전부 같은 행은 하나만 남깁니다. 수량이 다르면 진짜 두 번째 판매로 보고 더합니다.
- 그대로 두면: SKU-03의 하루 판매량이 약 1.5배로 부풀어 남은 일수가 실제보다 짧게 나옵니다.

**3. 음수 판매 수량 (2행)**
- 발견: 9/15 SKU-01 자사몰(8개와 -6개), 9/30 SKU-02 쿠팡(7개와 -3개).
- 처리: 음수 행만 뺍니다. 같은 날 양수 판매에서 빼서 합치지 않습니다(예: 8개와 -6개를 2개로 만들지 않음). 반품이면 재고에 이미 반영돼 있어 두 번 세는 꼴이고, 원인이 무엇이든 빼는 쪽이 판매 속도를 더 빠르게(보수적으로) 잡기 때문입니다.
- 양수에서 빼서 합치면: 속도가 느려져 재고가 충분해 보이는 쪽으로 기웁니다. 이 데이터에서는 결과가 같았습니다.

**4. 하루 판매량 급증 (SKU-04, 9/23에 270개)**
- 발견: 평소 하루 25~35개인데 하루만 270개(가운데 값의 9.6배). 행사였는지 입력 실수인지 데이터에 없습니다.
- 처리: 가운데 값의 3배를 넘는 날을 급증일로 보고, 뺀 계산과 넣은 계산을 둘 다 합니다. 결론이 같으면 그대로, 갈리면 판정 불가로 사람에게 넘깁니다.
- 그대로 두면(평균에 넣으면): 국내창고 16.3일이 9.8일, FBA_US 36.6일이 22.3일로 짧아집니다. 하루 행사 때문이었다면 생산을 필요 이상 앞당기게 됩니다.

**5. 최근 며칠 판매 기록 누락 (SKU-05, 10/2~10/4)**
- 발견: 10/1까지 매일 기록이 있다가 최근 3일만 없습니다. 품절인지, 데이터가 늦는지, 수요가 끊긴 건지 모릅니다.
- 처리: 빈 날을 0개로 채우지 않습니다. 빈 날이 있으면 안전 판정이 나오지 않습니다.
- 0으로 채우면: FBA_US가 45.6일 "안전"으로 나오는데, 실제로는 그사이 품절이었을 수 있습니다.

**6. 판매 이력이 7일뿐인 신제품 (SKU-06, 9/28 판매 시작)**
- 발견: 9/28 이전 기록이 없습니다.
- 처리: 5번과 같습니다. 출시 전 날짜는 빈 날로 보되 0으로 채우지 않습니다.
- 그대로 두면: 7일 표본으로 과도하게 확신한 판정이 나갑니다.

**7. 판매 기록이 한 건도 없는 제품 (SKU-08)**
- 발견: 재고는 1,200개 있는데 판매 기록이 한 건도 없습니다.
- 처리: 판정하지 않고 "판매 기록 없음"으로 판정 불가 처리해 담당자에게 넘깁니다. 메시지에는 재고 수량과 함께 "출시 전인지, 판매 데이터가 빠졌는지 확인해 주세요"라고 적습니다.
- 판정하지 않는 이유: 남은 일수는 재고를 하루 판매량으로 나눈 값인데, 판매 기록이 없으면 하루 판매량을 알 수 없습니다. 아직 출시 전이라 안 팔린 것일 수도 있고(그러면 1,200개는 충분합니다), 팔리고 있는데 판매 데이터만 빠진 것일 수도 있습니다(그러면 위험할 수 있습니다). 데이터로는 둘을 구분할 수 없어서, 숫자를 지어내 "안전"이나 "경보"라고 말하는 대신 사람이 확인하게 합니다.

**8. 재고 상태가 여러 가지 (판매가능, 입고예정, 이전중)**
- 발견: SKU-03 국내창고 입고예정 300개, SKU-07 FBA_US 이전중 450개. 둘 다 아직 창고에 없습니다.
- 처리: 판매가능만 계산에 넣고, 나머지는 "들어오면 며칠분" 메모로만 보여 줍니다.
- 그대로 두면: 아직 안 온 수량을 있는 것처럼 세는 거짓 안전.

**9. 기준일·재고·판매 날짜가 서로 다름 (기준일 10/6, 재고 10/5, 판매 10/4까지)**
- 처리: 재고는 경과일(1일)만큼 더 팔렸다고 보고 뺍니다. 판매 속도 계산 기간도 이틀 전까지로 맞춥니다. 경과일이 2일이면 안전 판정을 보류하고, 3일 이상이면 전부 판정 불가입니다.
- 그대로 두면: 어제 숫자를 오늘 숫자처럼 써서 재고를 많게 잡습니다.

**10. 리드타임이 유독 짧은 제품 (SKU-04, 14일)**
- 발견: 나머지 7개는 21~28일. 오타인지 실제로 빠른 제품인지 모릅니다.
- 처리: 값은 그대로 쓰고, 메모와 메시지 맨 아래 "마스터 경고"로 담당자가 확인하게 합니다.

**11. 재고 0을 표기하는 방식이 제각각**
- 발견: SKU-07 FBA_US는 "판매가능 0개" 행이 있고, SKU-05 국내창고는 행이 아예 없습니다. SKU-03 국내창고는 판매가능 행 없이 입고예정 행만 있습니다.
- 처리: 그 창고 행이 하나도 없으면 0으로 계산하되 "재고 행 없음, 0으로 계산" 표시와 "재고 행 확인" 할 일을 붙입니다. 어떤 상태든 행이 있으면 창고가 그 제품을 보고한 것으로 보고 판매가능 0으로 봅니다.
- 그대로 두면: 행이 없는 창고가 판정에서 조용히 빠집니다.

**12. 한 창고는 이미 품절인데 합치면 넉넉해 보임 (SKU-03, SKU-05)**
- 발견: 쿠팡·자사몰 판매가 SKU-03은 10/4, SKU-05는 10/1까지 이어지다가 10/5 재고에는 국내창고 판매가능 재고가 없습니다. 국내창고가 이미 바닥난 상태입니다. 반면 FBA_US에는 930개, 260개가 남아 있습니다.
- 처리: 창고별로 따로 판정합니다. 한 창고라도 경보면 그 제품은 경보, 경보는 없는데 한 창고라도 판정 불가면 판정 불가, 두 창고가 모두 안전일 때만 안전입니다.
- 합산하면: SKU-03이 36.4일 "안전"으로 나와 국내 품절을 놓칩니다.

**샘플 데이터에는 없지만 발생 가능한 데이터 오류**
- 채널·재고 상태·창고 이름의 오타나 다른 표기는 자동으로 고치지 않습니다. 채널 이름의 대소문자·공백 차이만 규칙으로 고치고, 그 밖의 오타는 그 행을 계산에서 빼고 해당 제품 항목에 "모르는 채널/상태/창고가 있음, 확인 필요" 메모를 띄워 담당자에게 알립니다.

## 주요 설계 결정과 그 이유

1. 하루 판매량은 최근 14일 평균입니다. 7일은 하루 변동에 흔들리고, 28일은 최근 추세를 늦게 반영합니다.
2. 급증일은 뺀 계산과 넣은 계산을 둘 다 하고, 결론이 갈리면 판정 불가로 넘깁니다. 행사였는지 입력 실수였는지 데이터로 알 수 없어서입니다.
3. 판매 기록이 빈 날은 0개로 채우지 않고, 빈 날이 있으면 안전이라고 하지 않습니다. 0으로 채우면 판매가 느려 보여 거짓 안전이 됩니다.
4. 재고는 판매가능만 셉니다. 입고예정·이전중은 아직 팔 수 없어서 "들어오면 며칠분" 메모로만 보여 줍니다.
5. 음수 판매 행은 원인과 상관없이 뺍니다. 양수 판매에서 빼서 합치면 판매가 느려 보여 안전 쪽으로 기웁니다.
6. 오늘 보낸 판정 목록(상태·긴급 여부·사유)과 같으면 다시 보내지 않습니다. 남은 일수는 비교하지 않아서 0.1일 변화로는 다시 보내지 않습니다.
7. 실패하면 종료 코드 1로 끝내고 원인을 로그에 남깁니다. 성공한 척 끝나지 않게 하기 위해서입니다.
8. 재고 스냅샷이 찍힌 뒤 지난 날수만큼 남은 일수에서 빼고, 3일 넘게 지난 재고로는 판정하지 않습니다. 오래된 재고 숫자를 지금 숫자처럼 쓰지 않기 위해서입니다.
9. 경보는 가장 짧은 창고의 남은 일수 순으로 정렬합니다. 가장 급한 제품이 맨 위에 오게 하기 위해서입니다.
10. AI 요약의 숫자는 사실 표 값과 그 정수 반올림만 허용합니다. 24.7일을 "25일"로 쓰는 것은 받아 주고, 없는 숫자는 거절합니다.
11. LLM 호출은 한 실행에 최대 3번(처음 1번과 재요청 2번)입니다. 라이브러리의 자동 재시도를 꺼서 이 횟수가 진짜 상한이 되게 했습니다.
12. API 키가 있으면 진짜 Claude 요약을, 없으면 가짜 요약을 씁니다. 키 없이 실제로 보낼 때는 가짜 문장 대신 정해진 문구를 보냅니다.
13. 담당자가 처리 표시한 제품을 알림에서 빼는 기능은 미뤘습니다. 슬랙 버튼을 받는 상시 서버가 필요해서, 하루 한 번 도는 배치와는 다른 일입니다.
14. 창고별로 따로 판정합니다. 합산하면 한 창고에 재고가 많을 때 다른 창고의 품절이 가려집니다(SKU-03).
15. 자사몰 주문은 국내창고에서 나간다고 가정했습니다. 창고가 FBA_US와 국내창고 둘뿐이고, 아마존 판매만 FBA에서 나가는 것이 자연스러워서입니다.

**9. 가정한 것**
- 채널과 창고 연결: 아마존 → FBA_US, 쿠팡·자사몰 → 국내창고. 창고가 둘뿐이고 아마존 미국 판매는 FBA에서 나가는 것이 보통이라 그렇게 봤습니다.
- 재고 스냅샷이 영업 마감 후인지 시작 전인지 모릅니다. 보수적으로 판단하여 (영업 시작 전에 스냅샷이 생성된다고 판단), 경보가 하루 일찍 울리는 쪽으로 구현하였습니다.

## 시간이 더 있었다면 할 일

**담당자가 처리했거나 비고를 단 제품은 다음 날부터 알림에서 빼는 기능.**

지금은 매일 아침 "오늘 상태표"를 보내기 때문에, 담당자가 어제 경보를 보고 이미 발주를 넣었어도 재고 숫자가 바뀌기 전까지 같은 경보가 매일 다시 갑니다. 판매 기록이 없는 제품(SKU-08)도 출시 전인지 단종인지 담당자가 확인을 끝냈더라도 매일 "판정 불가" 한 줄로 다시 뜹니다. 그래서 담당자가 제품에 "처리함"이나 비고를 남기면, 다음 날부터 그 제품을 경보와 판정 불가 목록에서 빼도록 만들고 싶습니다.
